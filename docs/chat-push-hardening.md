2026-09-15 스테이징 DB·Edge Function·프론트 배포 및 자동 검증 완료.
기능 코드 커밋은 `46447eee841cfc63d3a1864c047899347c4a372f`이며 운영에는 아직 반영하지 않았다.
이메일 인증/Auth 설정 및 수납·근무 파일럿 잠금은 이번 변경에 포함하지 않는다.

스테이징 검사 대상 16개가 통과했다(로그인 준비 4개 포함). 로컬 내부 상태를

요청 제한으로 중단된 1개는 제한 설정을 바꾸지 않고 재실행하여 통과했다.

## 바뀐 동작

- Edge Function은 `auth.getUser(token)`으로 확인한 사용자 ID만 사용한다.
  요청 JSON에서는 `messageId`만 읽으며, 발신자·수신자·학원·본문 지정은 무시한다.
- 로그인한 앱의 GET 요청에는 Web Push 공개키만 반환한다. VAPID 비밀키는
  함수의 서버 환경변수에만 보관하고 앱이나 Vercel에 전달하지 않는다.
- RLS와 푸시가 같은 내부 접근 판정을 사용한다. 활성 학원 구성원이면서
  전체방 구성원, DM 당사자 또는 선택 단톡방 참여자여야 한다.
- 서비스 역할 전용 `claim_chat_push`가 메시지의 실제 발신자와 소속 학원을 검증하고
  메시지별 발송 시도를 원자적으로 선점한다. 일반 계정과 비로그인은 호출할 수 없다.
- 제공자 인증이 끝난 뒤 기기별 `get_chat_push_device`가 발신자·수신자 권한,
  기기 활성 상태와 현재 소유자를 다시 검사한다. 퇴사, 방 참여 해제,
  로그아웃, 다른 계정으로 기기 재등록이 완료된 경우 발송에서 제외한다.
- 메시지 저장 RLS의 잘못된 `t.academy_id = t.academy_id` 비교를 실제
  메시지 학원과 방 학원의 비교로 수정했다. 새 메시지 시간은 서버가 지정한다.
- 서버 푸시, 브라우저의 앱 내 OS 알림, 서비스 워커 모두 제목 `씨닛`,
  본문 `새 메시지가 도착했어요. 앱에서 확인해주세요.`만 표시한다.
  제공자에는 이 문구와 이동용 `threadId`, `academyId`만 전송한다.
- Web Push는 HTTPS의 FCM·Mozilla·Apple 공식 푸시 호스트만 허용한다.
  임의 URL이나 내부 주소로 구독을 위조해 서버가 요청하도록 만들 수 없다.
- 제공자 오류 원문과 토큰은 로그나 HTTP 응답에 출력하지 않는다.
  기기 해제는 RPC의 요청 본문을 사용하여 토큰이 REST URL에 남지 않게 한다.
  제공자 종류·HTTP 상태·성공/실패/제외 건수만 확인한다.
  FCM은 `UNREGISTERED`, APNs는 410, Web Push는 404/410일 때 기기를 비활성화한다.
  일반적인 FCM 404(프로젝트 설정 오류 등)로 정상 기기를 끄지 않는다.
- 채팅·푸시 테이블의 일반 API 사용자에게 불필요한 TRUNCATE/TRIGGER 등 권한을 회수했다.

## 보장 범위와 의도적인 제한

- 메시지 생성 후 10분 이내 요청만 처리한다. 미래 시각과 오래된 메시지는 제외한다.
- 같은 메시지는 한 번만 발송을 시도한다. 성공 건수는 제공자가 요청을 수락한 건수이며
  사용자의 실제 수신·열람을 보장하지 않는다.
- `chat_push_dispatches`에는 메시지 ID와 선점 시각만 저장한다.
  메시지 삭제 시 함께 제거한다. 일반 사용자에게 조회·쓰기 권한은 없다.
- 일부 발송 후 연결이 끊겨도 중복 발송하지 않도록 자동 재시도하지 않는다.
  선점 직후 함수가 종료되거나 제공자 인증이 실패하면 알림이 누락될 수 있다.
  채팅 저장은 푸시와 분리되어 있으므로 앱에서 원문은 계속 확인할 수 있다.
- 제공자별 실패는 다른 제공자의 발송을 막지 않는다. 네트워크 요청은 10초 제한,
  제공자의 오프라인 보관은 120초로 제한한다.
- DB 권한 검사와 외부 제공자 전송은 하나의 트랜잭션이 아니다.
  마지막 검사 직후 권한이 회수되거나 이미 전송된 알림은 취소할 수 없다.
  따라서 알림에는 개인 정보가 없는 문구만 사용하며, 원문 조회에는 항상 RLS가 적용된다.
- 외부 제공자의 재전달이나 여러 기기로의 정상 알림까지 정확히 한 번을 보장하지 않는다.
- 계정별 메시지 생성 도배 제한, 발송 결과 장기 통계, 재시도 큐는 이번 범위가 아니다.
  현재 별도 큐/스케줄러/개발자 대시보드를 추가하지 않았다.

## 검증

- `npm run check:chat-push`: 실제 HTTP 핸들러의 인증·요청 검증, 발신자 위조 무시,
  권한 회수 후 제외, 제공자 실패 격리, 오류 개인정보 제거, 구독 URL 검증,
  서비스 워커·브라우저 알림 원문 제거.
- `npm run test:db`: 기존 084–089 회귀 및 090 역할 테스트.
  원장/매니저/선생님/위임 직원/초대 대기/비활성/외부인/비로그인,
  DM·선택방, 기기 비활성·소유자 변경, 만료·위조 발신자·잘못된 학원 소속을 검증한다.
  로컬 REST의 서비스 전용 RPC 접근 차단과 실제 DB를 사용하는 동시 요청 12건 중
  발송 시도가 한 번인 것도 확인한다. 합성 기기이며 외부 푸시는 발송하지 않는다.
- `SENTRY_UPLOAD_SOURCEMAPS=0 npm run build`: 운영용 빌드와 저장소 검사.
- `npm run test:e2e -- --project=chromium`: 기존 브라우저 회귀.
- Edge 타입 검사: `npx deno check --node-modules-dir=none --no-lock supabase/functions/chat-push/index.ts`.

로컬 확인 결과: 알림 단위 테스트 11개, DB 역할 테스트 084–090,
REST/동시 요청 테스트, 운영용 빌드, 기존 E2E 17개(로그인 준비 4개 포함)가 통과했다.
실제 로컬 Edge Runtime에서도 비로그인·위조 토큰 401, 다른 메시지 접근 403,
실제 로그인 토큰의 정상 요청, 중복 차단, 비활성 발신자 403을 확인했다.
알림 켜기 화면의 개인정보 안내는 라이트·다크 모드 및 동작 감소 설정에서 확인했다.
이 확인은 합성 계정과 수신 기기가 없는 방을 사용했으며 외부 푸시는 발송하지 않았다.
FCM/APNs/Web Push의 실제 기기 수신 확인은 스테이징 배포 후 남아 있다.

## 스테이징 배포 시 확인

1. 마이그레이션 → `chat-push` Edge Function → 프론트 순서로 동일 스테이징 프로젝트에 적용한다.
2. 역할별 실제 계정으로 전체방/선택방/DM을 시험한다.
3. 수신자의 브라우저/휴대폰에서 일반 문구만 표시되고 누르면 권한 있는 방만 열리는지 확인한다.
4. 퇴사·로그아웃·방 참여 해제 이후 새 푸시가 제외되는지 확인한다.
5. 발송 요청 중복, 잘못된 ID, 비로그인 요청을 확인한다.
6. FCM/APNs/Web Push 실기기 수신은 각 제공자의 자격 증명이 갖춰진 환경에서 따로 확인한다.

운영 적용은 스테이징 확인 후 동일 절차를 따른다. 이번 작업으로 운영 함수가
자동 갱신되지는 않는다. 새 함수는 새 RPC가 없으면 안전하게 발송을 중단한다.
