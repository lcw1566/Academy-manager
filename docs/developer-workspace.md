# 개발자 워크스페이스 운영 가이드

개발자 접근은 비밀번호나 이메일 하드코딩이 아닌 Supabase Auth 사용자 UUID의 서버
허용 목록으로 결정한다. 등록·해제에는 다음 서버 운영 명령을 사용한다.

```bash
npm run developer:access -- grant <사용자-UUID> developer
npm run developer:access -- revoke <사용자-UUID>
```

명령에 필요한 `SUPABASE_SECRET_KEY`는 로컬 비밀 환경에만 두고 브라우저나 Git에 넣지 않는다.
과거 `supabase/sql/078_developer_workspace.sql`을 운영 SQL Editor에 다시 적용하지
않는다. 기준 migration 이후 변경은 `supabase/migrations/`의 새 timestamp 파일로
진행한다.

## 운영 관제실

운영 개발자 화면은 서비스 익명 집계, 제품 피드백 접수·상태 변경, 장애와 배포 상태를
확인하는 외부 도구 링크로 구성한다. 피드백 상태 변경은 감사 로그에 기록된다.
Sentry, Vercel, Supabase, GitHub Actions 자체 화면의 상세 기능을 복제하지 않는다.
학생·보호자 연락처, 체크인 PIN, 학원 원본 데이터, 고객 계정 가장은 제공하지 않는다.
신고 이미지에 개인정보가 들어 있으면 문제 확인 목적 범위에서만 다룬다.

운영에서는 테스트 랩 버튼을 숨기는 데 그치지 않고 서버 RPC의 공개 진입점을
차단한다. `developer_test_environment_config`는 비어 있으면 비활성이다. 운영에서
이 값을 활성화하거나 합성 테스트 학원을 새로 만들지 않는다. 기존 운영 테스트 계정과
학원은 연결 데이터와 감사 이력을 먼저 확인한 뒤 별도 정리 여부를 결정한다.

## 스테이징 테스트 랩

스테이징에서는 별도 Supabase 프로젝트와 합성 학원으로 실제 원장·매니저·선생님·
초대 대기 계정, 권한 변경, 역할별 흐름을 검증한다. 수동 QA 계정과 자동 E2E 계정은
서로 다른 학원을 사용한다. 테스트 환경 활성화는 지정된 스테이징/로컬의 서버 운영
계정만 수행하며 감사 로그를 남긴다. 학생 연락처 등 운영 데이터를 복사하지 않는다.

자동 테스트 준비와 실행은 [E2E 가이드](./e2e-testing.md)와
[스테이징 환경](./staging-environment.md)을 따른다. 고객 학원에 개발자가 접근해야
하는 지원 기능은 현재 범위 밖이다. 필요해질 때 원장 동의, 짧은 만료, 최소 권한,
불변 감사 기록을 갖춘 별도 설계가 필요하다.
