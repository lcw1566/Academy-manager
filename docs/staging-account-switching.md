# 스테이징 실제 계정 전환과 동기화 경고 수정

## 변경 이유

`staging-teacher.e2e@example.test`에서 학생 조회·관리 권한이 꺼져 있으면 공통 스냅샷 로더가 학생 조회 RPC의 403을 동기화 실패로 표시했다. 직원 접근 정보·초대 계정 이력도 권한 없이 요청하고 있었지만, 두 API는 기존 오류 처리에서 부가 정보를 생략하고 있었다.

`get_my_academy_sync_access`가 기존 데이터 RPC와 동일한 서버 권한 판정을 반환한다. 공통 로더는 허용된 요청만 실행하고, 조회가 불가능해진 학생 목록은 비운다. RPC/RLS 권한은 그대로 유지한다. 일시적인 서버·네트워크 장애를 정상적인 빈 목록으로 바꾸지 않는다. 동시 요청만 공유하며 권한 결과는 저장하지 않는다.

## 사용자 확인

1. 스테이징을 새로고침하고 학원 선택 화면 또는 학원 화면 상단의 **테스트 계정 전환**을 펼친다.
2. 원장·운영 매니저·선생님·초대 대기 중 다른 계정을 선택한다. 실제 로그인 사용자가 바뀌고 학원 선택 화면으로 돌아온다. 저장하지 않은 입력은 사라진다.
3. 원장 계정의 **직원 → 선생님 → 권한**에서 학생 조회·관리 권한을 끈 뒤 선생님으로 전환한다. 학생 정보는 보이지 않고, 권한 부족만으로 동기화 경고가 뜨지 않아야 한다.
4. 원장이 보낸 채팅은 선생님 계정에서 상대방 메시지로 보여야 한다. 작성자 ID가 실제로 다르다.
5. 초대 대기 계정에서도 학원 선택 화면에서 원장으로 돌아올 수 있다. 계정 전환 자체는 초대를 수락하거나 역할·개인 권한을 변경하지 않는다.
6. 동시 채팅·브라우저 알림 비교는 별도 브라우저 프로필을 사용한다. 같은 프로필의 탭은 로그인 상태가 공유될 수 있다. 전환 전 기존 기기의 푸시 등록을 해제한다.

초대 대기는 고정된 테스트 계정 이름이다. 해당 계정으로 초대를 수락했다면 실제 상태는 수락 이후 상태이며, 전환 버튼이 상태를 초기화하지 않는다. 퇴사·비활성은 해당 테스트 직원의 실제 멤버십으로 검증한다.

## 서버 제한

- Edge Function `staging-test-login`은 지정된 스테이징 Supabase 프로젝트와 `SEENIT_ENABLE_TEST_LOGIN=true`가 모두 일치해야 동작한다. 로컬과 운영에서는 꺼진다.
- `getUser`로 확인한 호출자 UUID와 `developer_test_login_accounts`의 등록된 UUID만 사용한다. 브라우저는 역할 이름만 요청한다. 이메일·사용자 ID·비밀번호를 전달해 다른 대상에 접근할 수 없다.
- 테스트 학원의 개발자 등록이 활성 상태여야 한다. 다른 학원에 소속되거나 다른 학원을 소유하는 계정은 호출자와 대상 모두 제외한다. 비활성 소속도 다른 학원 소속이면 제외한다.
- 등록된 초대 대기·비활성 테스트 계정은 다른 테스트 계정으로 돌아갈 수 있다. 이 전환 자격은 실제 학원 데이터 권한이나 개발자 화면 권한을 부여하지 않는다.
- 계정별 세션은 일반 비밀번호 로그인으로 발급한다. 공유 테스트 비밀번호는 Edge Function secret `STAGING_TEST_ACCOUNT_PASSWORD`에만 두며 클라이언트 번들·응답·로그에는 포함하지 않는다. Supabase Auth의 기존 제한을 변경하지 않는다.
- 전환 요청과 세션 발급을 `developer_action_logs`에 기록한다. 대상 학원당 1분 12회 제한이 있다. 감사 기록 실패 시 토큰을 반환하지 않는다.
- 전환 성공 후 기존 계정의 기기 알림 등록·세션·화면 캐시를 정리하고 새로고침해 이전 요청·구독을 종료한다.
- 테이블은 마이그레이션만 적용하면 비어 있다. 운영에는 계정을 등록하거나 이 함수를 배포하지 않는다.

## 배포·검증 순서

1. 로컬 migration replay, `npm run test:db`, `npm run check:test-login`, 관련 Playwright, production build.
2. `npm run staging:db:dry-run`으로 두 forward migration만 확인한 뒤 staging DB에 적용.
3. 기존 테스트 계정 네 개가 준비된 상태에서 `node --env-file=.env.staging.local scripts/register-staging-test-logins.mjs`. 합성 데이터와 개인 권한은 초기화하지 않는다. 등록 요청도 감사 이력으로 남긴다.
4. 스테이징에만 함수 secret 두 개를 설정하고 `staging-test-login` 배포. 기본 JWT 검증 유지. 정상 사용자 인증은 함수 안에서도 별도로 확인한다.
5. `staging` 프런트엔드 배포 후 네 계정 간 전환, 선생님 경고, 채팅 작성자, 라이트·다크·동작 줄이기를 확인.

비상 중지는 스테이징의 `SEENIT_ENABLE_TEST_LOGIN=false`로 설정하거나 해당 등록 행의 `enabled`를 끄는 방식이다. 이미 발급된 정상 로그인 세션을 소급 취소하지는 않는다. 정리 작업도 감사 이력을 남긴다.

운영에는 이번 변경을 배포하지 않는다. 향후 운영 프런트엔드에 동기화 수정이 포함될 때는 `workspace_sync_access` DB migration을 먼저 적용해야 한다.

## 검증 기록 (2026-09-16)

- 로컬 두 migration 적용, DB 테스트 084~091 및 채팅 푸시 동시 요청 통합 테스트 통과.
- 전환 함수 단위 테스트 7개, Deno 타입 검사, production build/기존 guardrail 검사 통과.
- 로컬 Playwright 역할 협업 3개·개발자 랩 3개와 각 인증 setup 통과. 학생 조회 권한 제거 시 불필요한 RPC가 호출되지 않는지, 503 주입 시 경고가 유지되는지 확인.
- 스테이징에서도 SQL 091을 트랜잭션 안에서 실행하고 전부 롤백. 두 migration의 원격 이력 확인.
- 실제 스테이징 Auth/Edge를 사용한 선생님→원장→매니저→초대 대기→선생님 로그인 ID 변경, REST 직접 호출 차단, 선생님 동기화, 라이트·다크·동작 줄이기 확인. 테스트 데이터 초기화나 채팅 발송 없이 검증하는 `scripts/verify-staging-test-login.mjs` 제공.
- 스테이징 Advisors: 새 등록 테이블의 정책 없음(INFO)은 service-role 전용 의도, 새 동기화 RPC의 authenticated 실행(WARN)은 의도한 공개 범위로 권한 검사와 역할 테스트를 함께 확인. 기존 Auth 비밀번호 유출 방지 경고 및 미사용 인덱스 정보는 별도 작업. 이번에 해소했다고 간주하지 않음.
- 스테이징 전체 E2E는 기존 수동 테스트 데이터를 초기화하므로 이번 검증에서는 재실행하지 않음. 실제 OS 푸시 수신은 이 변경의 검증 범위에 포함하지 않음.
