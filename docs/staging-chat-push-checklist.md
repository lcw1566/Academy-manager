# 스테이징 채팅·푸시 확인 목록

접속: https://academy-manager-staging.vercel.app/

2026-09-15 스테이징 DB·푸시 함수·프론트 배포 완료. 운영에는 미반영.
대상 학원은 **씨닛 기능 테스트 학원**, 테스트는 **역할별 실제 계정**으로 진행한다.

## 준비

| 역할 | 이메일 |
| --- | --- |
| 원장 | staging-owner.e2e@example.test |
| 매니저 | staging-manager.e2e@example.test |
| 선생님 | staging-teacher.e2e@example.test |
| 초대 대기 | staging-invited.e2e@example.test |

- 첫 확인은 PC Chrome의 서로 다른 프로필 또는 PC 두 대를 권장한다.
  동일 프로필의 탭 두 개는 로그인 상태가 공유되므로 계정 분리에 사용하지 않는다.
- 새로고침 후 원장과 매니저로 각각 로그인한다.
- 받는 쪽에서 채팅의 **채팅 알림 켜기**를 누르고 브라우저·OS 알림을 허용한다.
- 이번에 Web Push 키를 연결했으므로, 이미 허용했더라도 새로고침해 기기를 등록한다.

## 순서대로 확인

| 확인 | 실행 방법 | 정상 결과 |
| --- | --- | --- |
| 1. 기본 송수신 | 원장이 매니저에게 DM을 보내고 매니저가 답장한다. 전체 채팅도 한 번 보낸다. | 서로 메시지가 보이고 새로고침해도 유지된다. |
| 2. 알림 개인정보 | 실제 개인정보 대신 `홍테스트 / test@example.test / 가상 메모` 같은 테스트 문구를 보낸다. 받는 쪽은 다른 화면이나 백그라운드에 둔다. | 알림 제목은 **씨닛**, 본문은 **새 메시지가 도착했어요. 앱에서 확인해주세요.**만 표시된다. 메시지 원문·이름·이메일·방 제목은 표시되지 않는다. |
| 3. 서버 푸시 | 받는 쪽의 씨닛 탭을 모두 닫되 브라우저는 켜 둔다. 다른 프로필의 원장이 새 DM을 보낸다. | 알림을 받고, 누르면 로그인 상태와 권한에 맞게 대화를 확인할 수 있다. |
| 4. 대화방 범위 | 원장과 매니저만 포함한 선택 단톡방에서 메시지를 보낸다. 선생님 계정도 확인한다. | 매니저는 대화와 알림을 확인할 수 있고, 참여하지 않은 선생님에게는 해당 방과 새 알림이 보이지 않는다. |
| 5. 로그아웃 | 수신 기기의 매니저 계정을 로그아웃한 뒤 원장이 새 메시지를 보낸다. | 로그아웃한 기기로 해당 계정의 새 알림이 오지 않는다. 재로그인 후에는 저장된 대화를 볼 수 있다. |
| 6. 퇴사·초대 대기 | 마지막에 원장이 테스트 직원을 내보낸 뒤 새 DM/단톡방 메시지를 보낸다. 초대 대기 계정도 수락 전 상태로 접속한다. | 내보낸 직원과 초대 대기자는 해당 학원 채팅에 접근하거나 새 푸시를 받지 못한다. |

퇴사 확인은 마지막에 한다. 실제 테스트 계정의 학원 소속이 변경되므로 다시 사용할 때는
원장이 재초대하거나 자동 테스트 준비 과정으로 테스트 학원을 복구한다.

## 이번에 직접 확인하지 않아도 되는 항목

- 같은 메시지 ID의 동시·반복 발송 요청: DB와 HTTP 핸들러 자동 테스트에서 확인.
- 발신자 위조, 잘못된 학원 소속, 비로그인 호출, 역할별 직접 RPC 요청: 자동 확인.
- 수납·근무 기능 공개 여부: 이번 배포에서 파일럿 잠금을 변경하지 않았다.
  기능 테스트 학원에서는 기존처럼 합성 데이터 테스트용으로 열릴 수 있다.

## 범위

- 현재 실기기 확인 대상은 **브라우저 Web Push**다. Android FCM/iOS APNs 발송 키는
  스테이징에 구성하지 않았으므로 네이티브 앱 푸시는 이번 수신 확인에 포함하지 않는다.
- 중복 방지를 위해 실패한 발송을 자동 재시도하지 않는다. 중요한 업무는 앱의 채팅에서 확인한다.
- 이미 외부 제공자로 전달된 알림은 회수할 수 없으므로, 로그아웃·퇴사 확인은
  해당 처리가 끝난 후 새로 보낸 메시지로 한다.
- 이상이 있으면 **사용한 역할 / 브라우저·기기 / 위 항목 번호 / 실제 결과**를 기록한다.
