# 씨닛 테스트 환경 운영 원칙

테스트의 대상은 계정 이름이 아니라 연결된 백엔드로 구분한다. 같은 테스트 이메일이라도
운영 Supabase에 있으면 운영 계정이고, 로컬 Supabase에 있으면 로컬 계정이다.

## 환경별 책임

| 환경 | 데이터 | 허용하는 테스트 | 금지 사항 |
|---|---|---|---|
| 로컬 개발 | 자동 생성 합성 데이터 | 개발, DB 역할 테스트, 전체 Playwright E2E | 외부 공개, 운영 키 사용 |
| CI | 실행마다 준비한 로컬 Supabase | PR마다 DB 테스트와 전체 E2E | 장기 상태 의존 |
| 스테이징 | 운영과 분리된 Supabase와 합성 데이터 | 배포 전 회귀·초대·알림 대체 흐름 | 운영 데이터 복제, 실제 결제·문자 발송 |
| 운영 | 실제 고객 데이터 | 읽기 중심의 최소 스모크 점검 | 데이터 초기화, 역할 변경, 파괴적 E2E |

현재 `npm run test:e2e`는 로컬 전용이다. 실행기는 Supabase API 호스트가
`localhost`, `127.0.0.1`, `::1` 중 하나가 아니면 시작 전에 중단한다. 운영 테스트
계정의 이메일이나 비밀번호를 이 실행기에 연결하지 않는다.

## 역할별 계정 원칙

- 원장, 운영 매니저, 선생님, 초대 대기는 각각 다른 Auth 사용자로 검증한다.
- 테스트마다 필요한 서버 데이터를 다시 준비하고 다른 테스트의 실행 결과에 의존하지 않는다.
- 브라우저 인증 상태는 역할별 파일로 분리하며 Git에 저장하지 않는다.
- 하나의 학원을 공유하는 동안은 worker를 1개로 유지한다. 병렬 실행은 worker별 원장과
  학원을 독립적으로 할당한 뒤에만 허용한다.
- 학생·보호자 연락처와 체크인 PIN은 합성값이어도 직접 테이블 조회 경로를 만들지 않는다.

## 운영에 존재하는 테스트 계정

운영 Supabase의 기존 테스트 계정 4개는 자동 E2E의 주 계정으로 사용하지 않는다. 별도
스테이징이 준비되기 전까지 다음 원칙으로 격리한다.

- 운영 스모크 점검 외에는 로그인하지 않는다.
- 실제 학생, 보호자, 결제, 급여 데이터를 연결하지 않는다.
- 직원 초대, 퇴사, 권한 변경, 데이터 삭제 테스트에 사용하지 않는다.
- 테스트 학원과 계정이 운영 집계·알림·과금에 미치는 영향을 확인한다.
- 삭제 여부는 연결 데이터와 감사 기록을 점검한 뒤 별도 작업으로 결정한다.

## 스테이징 도입 조건

스테이징은 운영과 다른 Supabase 프로젝트와 배포 주소를 사용한다. 운영 데이터를 복사하지
않고 마이그레이션으로 스키마를 재현하고 합성 seed를 넣는다. 환경 비밀은 GitHub의
staging Environment secret으로만 제공하고, 운영 secret과 이름 및 접근 승인을 분리한다.

스테이징 자동화를 연결할 때는 다음 조건을 모두 만족해야 한다.

1. 대상 Supabase project ref가 운영 project ref와 다르다.
2. 역할별 전용 테스트 계정을 사용한다.
3. 문자, 푸시, 이메일, 결제는 샌드박스 또는 로컬 수신함으로 향한다.
4. 초기화 RPC는 명시적으로 등록된 합성 테스트 학원만 변경한다.
5. 실패 증거에 인증 토큰이나 학생·보호자 개인정보가 포함되지 않는다.

구성과 실행 방법은 [`staging-environment.md`](./staging-environment.md)를 따른다. 스테이징
Playwright는 운영 project ref를 코드 수준에서 거부하고, 배포 앱의 환경/ref 표식까지
일치해야 시작한다.

## 기본 실행 순서

```bash
npm run supabase:start
npm run test:db
npm run test:e2e
```

CI도 동일한 순서로 실행한다. 운영 배포 직전에는 스테이징 E2E를 별도 승인 단계로 추가하고,
운영에서는 데이터 변경이 없는 스모크 점검만 수행한다.
