# 1인 운영자 최소 알림 체계

씨닛 자체 화면은 Sentry·Vercel·Supabase·GitHub의 상태를 복제하지 않는다. 각 서비스의
원본 알림을 사용하고 개발자 워크스페이스에서는 해당 화면으로 이동한다.

## 필요한 알림

| 서비스 | 최소 알림 | 대응 |
|---|---|---|
| Sentry | production에서 새 오류 또는 재발 오류가 처음 발생 | 영향 기능과 최근 배포를 확인하고 고객 작업을 막으면 즉시 배포 중지 |
| Sentry | production 오류가 5분 동안 5건 이상 | 반복 원인, 영향 사용자 수, 5xx 동반 여부 확인 |
| Vercel | 운영 또는 스테이징 배포 실패 | 실패한 환경·커밋을 확인하고 성공 전 DB/앱의 다음 단계를 진행하지 않음 |
| GitHub Actions | `Local Supabase and Playwright` 또는 `Synthetic recovery rehearsal` 실패 | 실패 커밋의 운영 병합 중지, 복구 연습 실패 시 백업 체계를 미검증 상태로 되돌림 |
| Supabase | DB·Auth·Storage·Edge 서비스 장애 및 사용량 한도 임박 | 상태 페이지와 로그를 확인하고 출결 임시 절차 시행 여부 결정 |

## 개인정보 원칙

알림 제목과 본문에는 학생·보호자 연락처, 체크인 PIN, 인증 토큰, 채팅 원문, 업로드
파일명이나 신고 이미지를 포함하지 않는다. 알림은 오류 코드·기능·환경·횟수·배포
커밋만 제공하고 원인 조사는 권한이 있는 원본 서비스에서 수행한다.

## 현재 확인 상태

- 저장소 CI는 보안 검사, DB 역할 테스트, 운영 빌드, 브라우저 E2E 실패를 GitHub
  Actions 실패로 표시한다.
- 합성 복구 연습은 매월 1일과 수동 실행 시 동작한다. GitHub 계정의 Actions 실패
  이메일 알림 수신 여부는 저장소 밖 설정이므로 별도 확인이 필요하다.
- 2026-09-24 읽기 전용 Sentry 점검에서는 최근 24시간 production 오류 이벤트가
  0건이었고, 지난 30일의 미해결 production 이슈가 2건이었다.
- 현재 연결은 Sentry 알림 규칙을 조회·변경할 권한이 없어 위 두 Sentry 규칙의 실제
  생성 여부는 확인하지 못했다. 고객 수용 전 Sentry의 Alerts에서 규칙과 수신 이메일을
  확인하고, 개인정보 없는 합성 오류 한 건으로 전달 경로를 시험해야 한다.

알림을 시험할 때 운영 고객 데이터나 실제 연락처를 오류 메시지에 넣지 않는다. 시험 후
합성 이슈는 해결 처리하고, 알림을 받지 못했다면 운영 준비 완료로 기록하지 않는다.
