# 씨닛 최소 복구·장애 대응 가이드

**현재 상태:** 2026-09-18 읽기 전용 점검에서 운영 Supabase 관리 API가 제공한
`available_backups`는 0건이었다. 이는 복구 가능한 백업을 확인하지 못했다는 뜻이지,
어떤 외부 백업도 존재하지 않는다는 증명은 아니다. 실제 복구 연습과 복구 성공 기록은
아직 없다. 첫 고객의 중요 데이터를 받기 전에 이 공백을 해소해야 한다.

[Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups)에 따르면
Free 프로젝트에는 자동 일일 백업이 제공되지 않아 정기적인 오프사이트 DB 백업이
권장된다. Pro 이상은 일일 DB 백업이 있지만, **Storage 객체의 파일 내용은 DB
백업에 포함되지 않는다.** 따라서 백업 범위는 Postgres 데이터뿐 아니라
`academy-drive`, `feedback-attachments` 같은 비공개 Storage 객체, 적용 migration,
Edge Function 소스, 배포 환경 설정·비밀값의 복구 방법까지 따로 정의해야 한다.
비밀값 자체를 이 문서나 Git에 기록하지 않는다.

## 고객 데이터 수용 전 최소 조건

1. 운영 플랜·백업 주기·보관 기간을 결정하고, 백업 생성과 실패 알림을 확인한다.
   Free를 유지한다면 암호화된 오프사이트 논리 백업과 별도 Storage 객체 백업의
   운영 절차를 먼저 구축한다. 개인정보를 로컬 PC나 스테이징으로 무단 복사하지 않는다.
2. 목표 복구 시점(RPO)과 복구 시간(RTO)을 고객에게 설명 가능한 수준으로 정한다.
   현재는 측정된 값이 없다. 확인 전에는 구체적 보장 수치를 약속하지 않는다.
3. 고객 데이터와 격리된 복구 프로젝트에서 **합성 데이터**로 DB와 파일을 복원하고,
   로그인·학원 권한·학생 출결·파일 접근을 검증한다. 복구 시간과 누락 범위를 기록한다.
   실제 고객 데이터를 복구 연습에 쓰려면 별도 승인·접근 통제·삭제 기록이 필요하다.
4. 백업 접근 권한은 운영자 최소 인원으로 제한하고, 복구 키와 백업 저장소 계정의
   복구 경로를 확인한다. 백업 파일·로그·작업 기록에 연락처와 PIN이 노출되지 않게 한다.

## 장애 중 확인 순서

1. 변경·배포를 멈추고 최초 발생 시각, 영향 학원·기능, Sentry 오류, Vercel 배포·
   5xx, Supabase DB/Auth/Storage/Edge 상태를 확인한다. 고객 원본 데이터나 토큰을
   사고 채팅·스크린샷·로그에 붙이지 않는다.
2. 최근 배포와 migration을 비교한다. 앱만 문제라면 이전 Vercel 배포 승격을 검토하되,
   현재 DB·Edge와 호환되는지 확인한다. 데이터 삭제나 DB 복원은 사람이 범위와
   복구 시점을 승인한 후 수행한다.
3. 출결이 중단되면 학원은 종이/오프라인 명단에 **최소한의 학생 식별자, 실제 시각,
   담당자**만 기록하고 안전하게 보관한다. 서비스가 복구되면 권한 있는 직원이 누락
   기록을 수동 입력하고 중복 여부를 확인한다. 명단은 학원 정책에 따라 폐기한다.
4. 복구 후 역할별 로그인, RLS, 출결·파일 접근, 알림, 오류율을 확인하고 원인·영향·
   조치·재발 방지를 기록한다.

운영 DB 덤프나 Storage 객체 다운로드는 이 가이드를 작성하면서 수행하지 않았다.
복구 가능성은 실제 백업과 격리 복원 검증 전까지 **미확인** 상태다.
